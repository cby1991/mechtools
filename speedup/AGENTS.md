## 1. 硬性约束（不可协商）

### R1 —— 全 Python，禁止 bat / psh  ✱

**任何形式的 `.bat` / `.cmd` / `.ps1` / `.vbs` 都不许进本仓库。**

- 不许用 PowerShell 弹窗（`subprocess` 调 `powershell` 一律算违规）
- 不许用 `.bat` 做启动器
- 需要交互 → 用 `src/speedup/dialogs.py`（tkinter）
- 需要编排 → 用 `src/speedup/cli.py` 的子命令
- 归档历史脚本时，`.ps1` / `.bat` **也不收**（见 §7 的归档规则）

> 理由：原先那套「`.bat` 找 Python + PowerShell 弹 WinForms 窗口」有三重开销
> （进程冷启动、临时 `.ps1` 写盘被杀软误报、多行脚本引号易被剥），
> 而且无法单元测试。已全部重写。

**验收方式**：`git ls-files | grep -E '\.(bat|cmd|ps1|vbs)$'` 必须无输出。

---

### R2 —— 不许把 stdout 强行改成 UTF-8  ✱

Windows 中文控制台的默认编码是 **cp936(GBK)**。把 `sys.stdout` 改成 UTF-8
会让中文**全部变乱码**。正确做法见 `console.ensure_safe_output()`：
**只改 `errors="replace"`，不动 `encoding`。**

已经有回归测试守着这条：`tests/test_console.py::TestStreamSafety::test_does_not_switch_encoding_to_utf8`。

**验收方式**：`grep -rn 'reconfigure(.*encoding' src/` 必须无输出。

---

### R3 —— 面向 Windows 中文环境

- 路径用 `pathlib` 或 `os.path`，**不要手拼字符串**
- 文件名比较一律 `os.path.normcase(os.path.abspath(...))`
- 要交给 Windows 老式宿主读取的文本（VBE/VB6 的 `.bas`、批处理、部分 ERP 接口文件）
  必须按 **GBK** 编码输出，不能用 UTF-8 无 BOM
- 本仓库自身的源码/文档统一 UTF-8

---

### R4 —— 破坏性操作必须先说清楚

- 覆盖已有文件前，必须在报告里明确写出「（覆盖旧文件）」
- 拷贝到目标文件夹时，**已存在同名文件一律跳过，绝不覆盖**
  （目标里的同名文件可能是人工改过的，覆盖不可逆）
- 删除任何东西之前先备份、先列出受影响路径、先确认

---

### R5 —— 业务数据不进仓库  ✱

**⚠️ 本仓库是公开的**（推在 GitHub 公开仓库上）。所以这条不只是「别把 xlsx 提交进去」，
而是**任何能反推出我们是谁、给谁干活、在做什么产品的内容都不许进来**。

- `.gitignore` 里已排除 `**/采购清单汇总*.xlsx` 等业务产物
- 测试一律用 `tmp_path` 造数据，不引用真实资料目录
- 代码、注释、文档、测试数据**一律用中性示例名**：
  零件名走「垫片 / 基座 / 关节支撑板」这类通用叫法，
  路径走 `D:\example\...`，**不许出现**真实客户名、项目名、内部目录名
- **`archive/` 刻意不进仓库**（`.gitignore` 里忽略）：那 65 个历史脚本原件里有
  内部路径、项目名和汇报文案，只在本地留档
- 提交前扫一眼 `git status`，别把客户图纸、BOM 带进去
- 拿不准就问主人，别自己判断「这个应该不敏感」

> 背景：2026-09-28 准备推公开仓库时做了一次脱敏，替换了 **300 多处**
> 真实零件名、客户项目名和绝对路径。同一件事别再干第二次 —— 写代码时就按中性名写。

## 2. 项目定位

`speedup` 是**车间提速工具集**，不是框架、不是库。目标是：

> 把原本「双击一个 bat 跑个小脚本」的活儿，做成**规范、可测、能积累**的 Python 项目。

⚠️ **本仓库是公开的**（GitHub 公开仓库）—— 写任何东西之前先想一遍
「这句话发到网上合适吗」。细则见 [R5](#r5--业务数据不进仓库--)。

判断一个改动该不该做，问三个问题：

1. 它让车间那几个人**少点几下鼠标**吗？
2. 它让出错时**更容易定位**吗？
3. 它让下次加工具**更省事**吗？

三个都是「否」的改动，别做。

**不做的事**：不引入 Web 界面、不做服务化、不追求跨平台完美
（Windows 优先，够用就行）。

当前形态：**一个双击就开的桌面图形界面**（`gui.py`）+ 一套等价的子命令。
界面是「壳」，业务逻辑全在 `tools/` 和领域模块里 —— 这条边界不许破（见 [R19](#r19--界面不许有自己的一套逻辑只许收参数--拼-argv--交给同一个-run-2026-09-28)）。

**设计取舍记录在 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)**，
本文件只记「必须遵守什么」和「为什么踩过坑」。

## 3. 目录约定

| 路径 | 放什么 | 能不能进包 | 进不进 git |
| --- | --- | --- | --- |
| `src/speedup/` | 真正在用的代码 | ✅ 进 wheel | ✅ |
| `src/speedup/tools/` | 一个工具一个模块 | ✅ | ✅ |
| `src/speedup/assets/` | 打包进程序的小素材（图标） | ✅ | ✅ |
| `tests/` | pytest | ❌ | ✅ |
| `docs/` | 架构说明（`INVENTORY.md` 除外，见下） | ❌ | ✅ |
| `examples/` | 素材生成脚本 | ❌ | ✅ |
| `archive/` | 历史一次性脚本原件 | ❌ **刻意放在 `src/` 外面** | **❌ 只在本地** |
| `docs/INVENTORY.md` | 归档台账（逐条列原始路径） | ❌ | **❌ 只在本地** |
| `_sandbox/` | 临时实验、一次性脚本 | ❌ | ❌ gitignore |
| `_backup/` | 拿掉的功能的备份 | ❌ | ❌ gitignore |

**为什么 `archive/` 不放 `src/speedup/archive/`？**
放在包内会被打进 wheel，还会被 pytest 的收集规则扫到，徒增噪音。
它们是「留档」，不是「模块」。

**为什么 `archive/` 和 `docs/INVENTORY.md` 不进 git？**
里面是内部脚本原件和它们的原始路径，而**本仓库是公开的**（见 [R5](#r5--业务数据不进仓库--)）。
它们留在本地，`uv run speedup archive` 照常能读。
`tests/test_cli.py::TestArchiveCommand` 会在没有该目录时**优雅跳过**，
所以新克隆的机器上跑测试不会红。

### 新增模块的落位规则

- 纯逻辑（无 IO）→ 直接放 `src/speedup/` 顶层，如 `matching.py`
- 跟文件格式相关 → 开子包，如 `excel/`
- 一个可被用户调用的工具 → `src/speedup/tools/`
- 界面 → `gui.py`；界面里**只准拼 argv**，业务逻辑一律不进来（见 [R19](#r19--界面不许有自己的一套逻辑只许收参数--拼-argv--交给同一个-run-2026-09-28)）
- 素材生成脚本（跑一次就提交产出物）→ `examples/`，别塞进 `src/`
- **所有常量放 `config.py`**，业务模块里不许出现裸数字（列号、行高、扩展名…）

## 4. 代码规范

> **本章包含 `R6`–`R11`、`R18`–`R24`、`R26`–`R32`。**
> `R12`–`R17` 是测试规范，在 [§5](#5-测试规范tdd)。
> 编号是累积的、只增不删，所以章节里的编号会**跳跃** —— 这是历史留下的，
> 不是漏写（每条编号的来历见 [§9 准则累积日志](#9-准则累积日志)）。

### R6 —— 常量集中，消灭魔数

列号、行高、扩展名、匹配阈值全部在 `config.py`。看到 `COL_NAME` 而不是 `3`。

### R7 —— 纯函数优先，IO 与决策分离

这是本项目最重要的结构约定。参考 `matching.py`：

```
match_score / build_matches / plan_copies     ← 纯函数，不碰磁盘，好测
scan_files / execute_copies                   ← 只有这两层真的读写磁盘
```

同理 `material.py` 把「规则匹配」与「读 PDF」拆开，
90% 的逻辑不装 pdfplumber 也能测。

**新写功能时先问：这部分能不碰磁盘/网络吗？能就拆出来。**

### R8 —— 中文宽度对齐用 `display_width`，不要 `len()`

汉字占 2 列。表格一律走 `console.render_table()`，
它用 `unicodedata.east_asian_width` 判定，并处理截断与 `row_prefixes` 缩进对齐。

**反面教材**：旧脚本用 `ord(ch) > 127` 判宽 —— `…`、`—` 这些会被算成 2 列，
表格就歪了。

### R9 —— 异常分层

- 用户能理解的失败 → 抛 `SpeedupError` 子类（`InputError` / `UnsupportedFormatError` / …）
- 由 `cli.py` 统一捕获并打印 `[失败] xxx`，**不吐 traceback**
- 未预期的异常**让它冒泡**（便于开发期定位 bug）—— 不要写 `except Exception: pass`
- 「顺手打开一下文件」这类附加功能失败 → 返回 `False`，不影响主流程

### R10 —— 注释写「为什么」，不写「是什么」

好注释：解释为什么不用 PowerShell、为什么弱特征只在标题栏认、
为什么同名文件不覆盖。
坏注释：`# 遍历列表`。

关键决策要在 docstring 里留下**取舍理由**，否则后人会「优化」掉它。

### R11 —— 类型注解 + 中文 docstring

公开函数必须带类型注解和 docstring。docstring 里写清：
参数含义、返回什么、抛什么异常、以及非平凡的设计理由。

### R18 —— 换行符统一 LF，归档区不做转换  `2026-09-28`

- 源码 / 文档统一 **LF**（`.gitattributes` 里 `* text=auto eol=lf`）
- **`archive/**` 必须 `-text`**：那里的脚本是逐字节留档，
  Git 一转换，`_PROVENANCE.md` 里记的 sha256 就对不上了
- **Python 写文本文件时必须显式 `newline="\n"`**：
  `Path.write_text()` 默认按 `os.linesep` 翻译，在 Windows 上会把 `\n` 变成 `\r\n`，
  悄悄破坏 LF 约定（本项目初始化时就是这么弄出 5 个 CRLF 文件的）

> 背景：本机全局 `core.autocrlf=true`，首次 `git add` 时每个文件都刷
> 「LF will be replaced by CRLF」警告。加 `.gitattributes` 显式钉死，
> 警告消失，跨机器 diff 也干净。

**验收**：`git status` 无换行符警告；`git check-attr -a archive/README.md` 显示 `text: unset`。

---

### R19 —— 界面不许有自己的一套逻辑，只许「收参数 → 拼 argv → 交给同一个 `run()`」  `2026-09-28`

图形界面（`gui.py`）**不得直接调业务函数**。它只做两件事：

1. 把控件里的值拼成 argv（`plan_copies` / `execute_copies` 那种「拼装与执行分离」的路子）
2. 交给 `cli.build_parser().parse_args([name, *argv])` 解析，再调 `module.run(args)`

拼 argv 那一步单独抽成 `ToolPage.build_argv()`，**不依赖任何窗口**就能测。

> 背景：一旦界面另写一套调用，就会出现「界面上能跑、命令行不行」（或者反过来）
> 这种最难查的 bug —— 两套逻辑同时存在，改一处忘一处。
> 现在菜单、命令行、图形界面三条入口共用一条执行路径。

**验收**：`tests/test_gui.py::TestBuildArgv::test_argv_survives_the_real_parser`
（界面拼出来的 argv 必须能被真解析器吃下去）。

### R20 —— 新增工具必须同时配图形界面表单，否则测试不通过  `2026-09-28`

往 `tools/TOOL_MODULES` 加工具的同时，**必须**在 `gui.TOOL_FIELDS` 里补一份字段定义。
忘了配的工具不会出现在界面上，用户会以为「工具没了」。

`Field` 的每个 `dest` / `flag` 都必须是该工具 argparse 里真实存在的属性，
`tests/test_gui.py::TestFieldContract` 会逐个喂给真解析器验一遍。

### R21 —— 日志区必须等宽字体，且 CJK 恰好是 ASCII 的两倍宽  `2026-09-28`

界面里的日志框（`BasePage.log`）必须用 `console.MONO_CANDIDATES` 里选出来的字体，
理由：`console.render_table` 是按**显示宽度**对齐的，换成比例字体整张表就错位了。
另外 `display_width` 假设「中日韩文字 = 2 列」，字体也得真的满足这个前提。

> 背景：界面上跑 `gbcopy` 会输出 130 多列的匹配表，字体一错就完全没法看。

**验收**：`tests/test_gui.py::TestFonts`（`measure("W") == measure("i")` 且 `measure("中") == 2 × measure("W")`）。

### R22 —— `pythonw.exe` 下 `sys.stdout` 是 `None`，必须先补丢弃流  `2026-09-28`

双击快捷方式走的是 `pythonw.exe`（为了不要黑框），此时 `sys.stdout` / `sys.stderr`
是 `None` —— 任何一句 `print()` 直接抛
`AttributeError: 'NoneType' object has no attribute 'write'`。

**`cli.main()` 和 `gui.launch()` 的第一件事必须是 `console.ensure_streams()`**，
它给这两个流接一个 `os.devnull` 空流。

> 另外：判断「还有没有控制台」要在 `ensure_streams()` **之前**做
> （`had_console = sys.stdout is not None`），否则这个信息就没了 ——
> 没有控制台时开不了图形界面，只能弹系统对话框，不能 `print`。

**验收**：`tests/test_gui.py::TestPythonwMode`。

### R23 —— 提交信息这类临时文件不许写在仓库里  `2026-09-28`

`git commit -F <文件>` 用的提交信息文件，**必须写到系统临时目录**，
不许在仓库根目录建 `_commitmsg.txt` 这类文件。

> 背景：本项目初始化时就这么干过 —— 文件建在仓库根，`git add -A`
> 顺手把它也 stage 了进去，于是临时文件进了提交历史。见 [P10](#p10--git-add--a-把仓库里的临时文件一起提交了)。
>
> 不写 `.gitignore` 挡它：根本问题是「仓库目录里不该出现我的中间产物」，
> 加规则只是把症状藏起来，下次换个文件名照样中招。

**验收**：`git ls-files | grep -iE '_commitmsg|commitmsg'` 无输出。

### R24 —— 从用户的文件里「读一份数据」时，多份候选必须明确挑一份，并说出来  `2026-09-28`

适用范围：任何「从用户给的文件里挑出一组数据」的地方（工作表、分区、命名空间、配置节…）。

- **不许把多份候选静默合并。** 合并看起来"更全"，实际是把用户**明确划出去**的
  数据又拉了回来（见 [P12](#p12--把工作簿里所有工作表的名称列合并成一个名单)）
- **选法要确定，而且优先按名字、不按位置。** 位置会因为别人插一页就变
- **输出里必须写明「用了哪一份、忽略了哪几份」** —— 用户看不到你的选择过程，
  就只能靠结果反推，而结果往往是错的
- **必须留一个手动指定的入口**（如 `gbcopy --sheet`）
- **用户已经手动指定时，不许再提醒他用这个入口** —— 他已经做过决定了

**验收**：`tests/test_e2e.py::TestMultiSheetListing`
（含「只读主表」「提醒会出现」「`--sheet` 能覆盖」「指定后不再啰嗦」四条）。

### R25 —— 「同步到远端」必须从本地仓库发，不许改临时副本  `2026-09-29`

适用范围：任何把本仓库内容推送到别处（GitHub 子目录、镜像仓库、发布包）的动作。

本仓库的布局是**非对称**的：

```
本地  <项目根>/            ← 仓库根 == 工具内容本身
远端  cby1991/mechtools
        └── speedup/       ← 我们落在这一层
```

推送走 `sync-to-github.py`：临时目录建外壳仓库 → 拉远端 → `git bundle` 搬对象 →
`git read-tree --prefix=speedup/` → 提交推送。**临时目录用完即删。**

> **脚本位置已迁出本仓库**（2026-09-29）。原来 `speedup/sync-to-github.py` 只懂
> speedup 一个仓库；mechtools 组织下多了 `swauto` 之后，它升级成了**多项目同步器**，
> 搬迁到组织层：`D:\WorkSpace\projectmanage\mechtools\sync-to-github.py`。
> 用法 `python sync-to-github.py all`（或 `speedup` / `swauto` / `--list`）。
> **本仓库里不再放同步脚本** —— 它是跨项目的运维工具，不属于任何单个工具。

- **一律改本地文件，不要改外壳仓库里的副本。** 外壳仓库每次重建，改动必然丢失
  （踩过：改了远端 README 的 clone 占位，推完发现远端还是旧的，见 [P13](#p13--改在临时副本上的东西，一同步就被本地覆盖回去)）
- **同步前本地工作区必须干净。** 脚本会拦，不要绕过 —— 脏工作区推上去的东西
  和本地看到的不一致，排查起来极难
- **本地是唯一真相源。** 远端任何手工改动，下次同步都会被覆盖。要改就改本地
- **每次同步后必须回读远端确认**（`gh api .../contents/<path>`），
  不能只看 `push` 的返回码
- **多项目必须共用同一个外壳仓库。** 每个项目各建一个外壳、各自 push，
  第二次会被拒（远端已前进）。脚本已按「一个外壳、依次 read-tree、一次 push」
  实现，别改成循环里各自 push

**验收**：`sync-to-github.py speedup --dry-run` 能在脏工作区时拒绝执行；
同步后远端 `speedup/README.md` 的内容与本地 `git show HEAD:README.md` 一致。

### R26 —— 从图纸里提取结构化信息，按**坐标**切，不按文字流顺序  `2026-09-29`

适用范围：任何从 PDF / CAD 导出图纸里「按栏目」取内容的地方。

- **一律用「标题锚点 + 坐标约束」定位栏目，禁止依赖 `extract_text()` 的行顺序。**
  工程图的图框标题栏和图示内容在纵向范围上重叠，`extract_text()` 吐出来的顺序
  是交错的 —— 技术要求条目里会夹进「零 件 代 号」「描图」「借(通)用件登记」，
  直接按行取就是一堆垃圾。
- **切分条件优先用「与标题左边界对齐」。** 实测技术要求条目和标题的 `x0`
  完全相等，而图框标题栏文字贴在页面左边缘，用 `x0` 一刀就分开了。
- **对齐容差要小，而且不能是唯一防线。** `TECH_ALIGN_TOLERANCE = 6.0` 既在过滤
  也在冒险：放开就会把图面尺寸数字收进来（实测有一份图纸的 `0.00` 只差 7pt）。
  所以条目编号另设一道更严的闸 —— **只认顿号 `1、`，不认半角点**。
- **「读不了」和「图纸没写」必须分开。** 前者给 `error`，后者给空结果。
  混在一起，汇总报告里就说不清到底是工具坏了还是图纸缺信息（见 R9 异常分层）。
- **措辞不可穷举，输出要能容纳意外。** 同一件事实测有七八种写法
  （`表面阳极氧化为本色` / `表面本色氧化处理` / `表面本色硬质阳极氧化` /
  `表面处理参考CMF`…），所以规则是「**挑关键词、按原文顺序拼回去**」，
  而不是「解析成结构化字段」。图纸只写「参考 CMF」这种**指向外部文件**的情况，
  **原样带走，不许当没找到** —— 那是「要去查别的文件」的信息，不是缺失。
- **关键词表要「最长优先」。** `硬质阳极氧化` 必须赢过 `阳极氧化`，
  否则「硬质」丢了 —— 硬质阳极氧化的膜更厚，是完全不同的报价。

**验收**：`tests/test_techreq.py`（含四条回归：标题栏文字被排除、标题上方被排除、
尺寸 `0.00` 不算条目、CMF 原样保留）。

### R27 —— 报「没找到」时，必须把「我实际扫到了什么」一并说出来  `2026-09-29`

适用范围：任何「在用户给的位置里找东西、找不到」的场合。

- **只报「没找到」是不够的。** 用户看不见你的搜索过程，只能从结果反推 ——
  而反推往往是错的。实测踩到：脚本报「2 个零件没有同名图纸」，用户的第一反应
  是「你肯定跑去别处找同名文件了」，而不是「那两个零件确实没图纸」。
- **把扫描范围和实际命中打出来。** 找不到图纸时，顺手列出那个文件夹里
  **实际存在**的 PDF：
  `这个文件夹（含子目录）里共有 5 张 PDF：A.PDF、B.PDF…`
  —— 用户一眼就能分清「东西真不在」和「在，只是名字对不上」。
- **提示要能自己解释自己。** 后面跟一句判断方法：
  「上面缺的零件若不在这批文件名里，就是图纸和模型的名字对不上。」
- **同名文件可能不止一份，内容还不一样。** 别假设「同名 = 同一份」。
  实测同一个零件名在三个版本目录里都有图纸，其中两份写「参考CMF」、
  一份写具体的阳极氧化 —— 对照错了图纸，就会以为工具读错了文件。
  匹配时锁死「同一个目录」，并在提示里点明是哪个目录。

**验收**：`tests/test_e2e.py` 的 `test_missing_pdf_lists_the_folder_pdfs`
与 `test_missing_pdf_when_folder_has_none`。

### R28 —— 读 PDF 只取「落在页面范围内」的内容  `2026-09-29`

适用范围：任何用 pdfplumber（或同类库）读 PDF 文字的地方。

- **`page.extract_words()` 会把页面之外的内容也吐出来。** PDF 的页面外可能还有
  东西 —— 两张图拼在一起、导出时画布比页面大，等等。这些内容**在屏幕上根本
  看不见**（被裁掉了），但它们仍然留在 PDF 的内容流里。
- **一律走 `pdfpage.words_in_page(page)`，不要直接 `page.extract_words()`。**
  实测踩到：一张 595pt 宽的图纸上，`x0=627.9` 处藏着**另一套「技术要求」栏**
  （写着「外观件，表面电镀处理」），而页内那套写的是「表面本色硬质阳极氧化」。
- **这类错最阴险的地方是「结果看起来完全合理」。** 程序给出的「电镀」是个合法的
  表面处理，没有任何异常信号跳出来。全盘 113 个「模型+图纸」配对里只有 5 个中招，
  而且**哪几个中招取决于两套词在 `extract_words()` 里的先后顺序**（不稳定）——
  同一批图纸里 3 张碰巧读对、2 张读错。用户不回去核对原图，根本发现不了。
- **容差要留。** PDF 坐标常带零点几 pt 的浮点误差，页边卡死 0 会误杀贴着边线的字。

**验收**：`tests/test_pdfpage.py`（页外右侧 / 下方 / 左侧的词被丢弃、贴边词不被误杀）。

### R29 —— 重依赖必须做成可选，且运行时优雅降级  `2026-09-29`

适用范围：任何要引入「体积大 / 装得久 / 平台绑」的第三方依赖的功能。

- **不放进主依赖。** 进 `pyproject.toml` 的 `[project.optional-dependencies]`
  （本项目叫 `images`），用 `pip install speedup[images]` 补。
- **运行时优雅降级，绝不抛异常。** 提供 `is_available()` 让调用方先问一句；
  真正干活的函数在缺依赖时**返回带 `error` 的结果**，不是 raise ——
  与 `material.find_material_in_pdf` 的既有约定保持一致。
- **测试必须能跳过。** 需要重库的用例用 `pytest.importorskip(...)`；
  纯计算部分（相机位置、尺寸换算）**不依赖重库**，必须无条件测到。
- **缺依赖时要说人话。** 命令行明确提示「没装 X，已跳过 Y（装法是 Z）」，
  不要静默什么都不做，也不要只丢一句 ImportError。

**背景**：给采购清单加轴测图，选了 cadquery。它自己不大，但拖进来
OCP + vtk + numpy + scipy + numba + trame×5，`uv pip install` 跑了 **4 分 46 秒**。
对只需要「读 PDF 出清单」的用户，这份负担完全没必要 ——
轴测图是锦上添花，不该让主流程替它买单。

**验收**：`tests/test_thumb.py` 的 `TestIsAvailable` 与 `TestRenderWithoutCadquery`
（打桩 `_load_cadquery` 返回 None，验证降级不崩）。

### R30 —— 新增依赖必须同步进「环境体检」  `2026-09-29`

适用范围：任何引入新第三方库（必需或可选）的改动。

- **新依赖要在 `run_doctor()` 的清单里露脸**，写清「哪个版本 + 用来干什么」。
  用户反馈「跑不起来」时，第一件事就是让他跑体检 —— 清单不全，这一步就白做。
- **必需依赖缺失 → 体检返回 1**；**可选依赖缺失 → 只提示，仍然返回 0**
  （判定时认名字里的「（可选）」标记）。把可选项判成失败会让人以为整个环境坏了。
- **隐式依赖也要提一句**。cadquery 的渲染靠 `vtk`，装了 cadquery 却没 vtk
  照样出不了图 —— 探针里顺带确认一下，别让用户对着「cadquery 2.8.0 ✔」发愁。
- **贴一句「装法」**。测出缺什么，就顺手告诉人怎么补（`uv pip install xxx`），
  别只报「不可用」。

**背景**：做完表面处理提取和轴测图之后，体检清单还是老的四项 ——
`pillow`（嵌图必需）和 `cadquery`（出图可选）**都没进清单**。
用户问「我新加的这些功能所需的库，体检都能检测到吗」，一查才发现漏了。
特别是 pillow：缺了它**图片会静默不嵌**，这种问题最难查。

**验收**：`tests/test_cli.py::TestDoctor` 的 `test_reports_pillow`、
`test_reports_optional_cadquery`、
`test_missing_optional_dependency_is_not_a_failure`。

### R31 —— 新增命令行开关，必须同时补 GUI 表单（要有**反向**检查）  `2026-09-29`

这是对 [R20](#r20--新增工具必须同时配图形界面表单否则测试不通过-2026-09-28) 的补强。

- **两处都要改**：`tools/<名>.py` 的 `add_parser()` **和** `gui.py` 的 `<名>_FIELDS`。
  漏了后者的后果不是报错，而是**这个功能在界面上彻底隐形** ——
  用户点不到、也搜不到，只会觉得「说好的功能呢」。
- **契约测试必须双向查**：
  * 正向（R20 已有）：GUI 字段 → argparse 得认
  * **反向（R31 新增）**：argparse 的每个 `--option` → GUI 里得有对应控件
  只做正向的话，「参数加了、界面忘了」这种漏挂**测试是全绿的**。
- **反向检查别依赖 `cli.build_parser()` 的内部结构**（`_subparsers` 那串是私有的），
  直接 `ArgumentParser()` + `module.add_parser(subparsers)` 自己搭一个，
  从 `subparsers.choices[name]._actions` 里取 `option_strings`。

**背景**：加 `--with-image` 时只改了 `add_parser`，忘了 `GBBUILD_FIELDS`。
主人问「现在可以自动输出图片了吗」才发现 —— 他在界面上根本找不到那个勾选框，
而当时的 445 条测试**全绿**。

**验收**：`tests/test_gui.py::TestFieldContract::test_every_argparse_option_is_exposed_in_gui`。

### R32 —— 「自动」的能力要由用户按下开关，不许静默执行  `2026-09-29`

适用范围：任何会**改变用户环境或产生外部副作用**的自动行为
（装包、下载、覆盖文件、联网提交…）。

- **体检只报告，不自动修。** 想修，用户得主动点一下
  （`doctor --install` / 界面上「补齐依赖」按钮）。两处都要有，缺哪个都别扭：
  命令行用户要 flag，双击快捷方式的用户要按钮。
- **命令必须可见。** 执行前把完整命令打出来，让人知道你要干什么；
  进度**直接透传终端，不静默** —— 大包要几分钟，静默会让人以为程序卡死。
- **失败要给出能照抄的手工命令**，而不是干说一句「失败」。
- **uv 要钉住解释器，且 `--python` 只能放在 `install` 之后**：
  * 对：`uv pip install --python <解释器> pkg`
  * 错：`uv pip --python <解释器> install pkg` ← **实测直接报 Usage**
  不钉解释器的话，从图形界面启动时**没有激活任何环境**，会装到别处去 ——
  用户看到的现象是「明明装成功了却还是不可用」。
- **别想当然用 `python -m pip`**：uv 建的 venv **默认不带 pip**（实测确认）。

**背景**：主人问「检测到缺库能不能自动下载」。技术上完全能做，但我把顾虑摆出来后
他也认同：装包 = 改环境 + 联网 + 可能几分钟，**不该由工具单方面决定**。
于是做成「用户按了才装」。
顺带踩到 uv 的参数顺序坑：我先写成 `uv pip --python X install`，
**拿真 uv 跑 `--dry-run` 才发现它直接报 Usage** —— 这种"看起来对"的命令
必须实跑一次，光靠想会错。

**验收**：`tests/test_cli.py` 的 `TestPickInstaller` / `TestInstallCommand` /
`TestDoctorInstall`，以及 `tests/test_gui.py` 里体检页第二按钮的三条。

## 5. 测试规范（TDD）

> **本章包含 `R12`–`R17`。** 代码规范在 [§4](#4-代码规范)，编号会跳跃，见那里的说明。

### R12 —— 先写测试，再写实现

长期逻辑组件一律 TDD：红 → 绿 → 重构。

流程：

```bash
uv run pytest -q                                    # 先看红
# 写实现
uv run pytest -q                                    # 看绿
uv run pytest -q --cov=speedup --cov-report=term-missing
```

### R13 —— 测试不许碰真实数据

- 用 `tmp_path` / `make_files` 夹具造数据
- 不许硬编码 `D:\example\...` 这种真实路径
- 不许在测试里真去开资源管理器（`tests/conftest.py` 里有 autouse 夹具打桩）

### R14 —— 测试里也别写业务魔数

需要常量就从 `speedup.config` 取。这样改常量时测试会跟着走，
不会出现「测试还在断言旧的列号，结果永远绿」这种假安全感。

### R15 —— 已知边界要留回归测试，注释里写明原因

例子：

- `test_aluminium_grade_with_temper_is_strong` —— 旧规则漏掉 `2A12-T4`，
  源码注释却声称支持。这种「注释与实现对不上」的 bug 必须靠测试钉死。
- `test_does_not_switch_encoding_to_utf8` —— 钉死 R2。
- `test_tools_are_wired_to_the_same_run_path` —— 钉死「菜单与命令行同一条路径」。

### R16 —— GUI 测试要能跳过

真实点窗口的用例标 `@pytest.mark.gui`，默认跳过。
其余逻辑必须能在无图形界面环境跑通（用 monkeypatch 打桩）。

### R17 —— 测试失败先怀疑测试

本项目实测：8 个首轮失败里 **7 个是测试写得不对**（样例数据选得不严谨），
只有 1 个是真功能缺口。所以看到红，先问「我的断言真的对吗」。

## 6. 新增一个工具的标准动作

按顺序做完，缺一不可：

1. 在 `src/speedup/config.py` 加常量（如果有）
2. 建 `src/speedup/tools/<名字>.py`，定义：
   - `NAME`（子命令名，小写）
   - `TITLE`（中文标题，菜单和界面里显示）
   - `SUMMARY`（一句话说明）
   - `add_parser(subparsers) -> ArgumentParser`
   - `run(args) -> int`
3. 在 `src/speedup/tools/__init__.py` 的 `TOOL_MODULES` 里加一行
   → 菜单和子命令会自动出现，**不需要改 `cli.py`**
4. **在 `src/speedup/gui.py` 的 `TOOL_FIELDS` 里补一份表单**（见 [R20](#r20--新增工具必须同时配图形界面表单否则测试不通过-2026-09-28)）
   - 每个 `Field` 的 `dest` 必须是 argparse 里真实存在的属性名
   - `flag` 用命令行开关原文（如 `"--min-score"`）；位置参数写 `flag=None`，
     且**声明顺序必须和 `add_argument` 顺序一致**
   - 界面表单不会自动出现，忘了配这个工具就「从界面上消失」了
5. 在 `tests/` 加测试
   - 纯逻辑直接测；界面表单由 `TestFieldContract` 自动覆盖，不用另写
6. 在 `README.md` 的「[有什么工具](README.md#1-有什么工具)」表 +「工具详解」里补一节
7. 在 `TODO.md` 更新状态，收尾时按 §7 回写本文件

**注意**：不要在 `add_parser` 里用 `parser.set_defaults(_run=run)`。
那会让 argparse 在构造时就绑死函数对象，导致菜单、命令行、测试三条路径不一致
（这个坑踩过，见 [P3](#p3--parsersset_defaults_runrun-把函数对象提前绑死)）。
`cli.py` 统一按命令名从 `TOOLS` 取模块再调 `run()`。

**任何一次改动，收尾时按这个清单走：**

### 7.1 先清 TODO

打开 `TODO.md`：

### 7.3 新准则怎么加

2. **溯源表**加一行（编号 / 规则 / 日期 / 来自）
3. **具体理由**补一段，写清「不做这条会发生什么」
4. 能自动化检查的，**顺手写成测试**

## 8. 踩坑记录

按「现象 → 根因 → 修法」记，便于搜。

### P1 —— Windows 中文控制台乱码

- **现象**：脚本输出中文全是乱码
- **根因**：脚本里写了 `sys.stdout.reconfigure(encoding="utf-8")`，
  而中文 Windows 控制台是 cp936。**编码改了，控制台没改**，必然乱码。
- **修法**：只设 `errors="replace"`，保持平台原编码 → [R2](#r2--不许把-stdout-强行改成-utf-8-)
- **谁守**：`TestStreamSafety::test_does_not_switch_encoding_to_utf8`

### P2 —— PowerShell 弹窗的三重代价

- **现象**：点一下要等一两秒；杀软偶尔报警；传多行脚本时引号被吃掉导致语法错误
- **根因**：用 `subprocess` 起 `powershell -Command` 弹 WinForms 窗口，
  每次都是进程冷启动；还借 `OpenFileDialog` 让用户「选文件夹里的 .stp」来间接选文件夹
- **修法**：换 `tkinter.filedialog` → [R1](#r1--全-python禁止-bat--psh-)
- **遗留取舍**：Tk 的目录选择框不是资源管理器同款大窗口（已在 README 注明）

### P3 —— `parser.set_defaults(_run=run)` 把函数对象提前绑死

- **现象**：测试里 monkeypatch 工具模块的 `run` 不生效；菜单和命令行走了两条路径
- **根因**：`set_defaults` 在**构造 parser 时**就存了函数对象，
  之后改模块属性影响不到 `args._run`
- **修法**：`cli.py` 统一 `TOOLS.get(command).run(args)`；
  工具模块里不再 `set_defaults(_run=...)`
- **谁守**：`test_tools_are_wired_to_the_same_run_path`

### P4 —— autouse 夹具打桩打太宽，把自己想测的东西也桩掉了

- **现象**：`test_osutil.py` 全红，`open_with_default_app` 直接返回 `True` 但没走任何逻辑
- **根因**：`conftest.py` 的 autouse 夹具把 `speedup.osutil.open_with_default_app`
  也桩了，导致真实实现永远测不到
- **修法**：只桩**使用点**（`speedup.tools.*.open_with_default_app`），不桩 `osutil` 本体
- **教训**：打桩要打到「最近的调用点」，越靠近被测对象越好

### P5 —— 注释声称支持的格式，实现其实不支持

- **现象**：`material.py` 的强特征注释写着 `2A12-T4`，实测匹配不上
- **根因**：规则是 `\d{3,4}[-][A-Za-z]\d+`，要求 3~4 位数字打头，
  `2A12` 只有 1 位数字打头，压根匹配不了「注释」里的例子
- **修法**：补一条铝合金牌号专用规则 `\b[1-8][A-Za-z]\d{2}[-－][A-Za-z]\d+\b`（强），
  `[1-8][A-Za-z]\d{2}`（弱，仅标题栏）
- **教训**：**注释里的例子要当测试用例跑一遍**。不然注释会变成谎言。

### P6 —— 表格行标记导致表头错位

- **现象**：给数据行加 `!` / `X` 前缀后，表头比数据行左移 2 列
- **根因**：前缀不参与宽度统计，但表头没补等宽缩进
- **修法**：`render_table` 增加 `indent` 参数，默认自动取 `row_prefixes` 的最大宽度

### P7 —— `.lnk` 里的路径有两种编码，搜不到不等于写坏了

- **现象**：在项目目录建快捷方式，文件里能搜到 `pythonw.exe`（UTF-16）；
  在 `tmp_path`（C 盘）建，搜不到，一度以为写坏了
- **根因**：`.lnk` 的路径存在**两个**地方：
  `StringData` 段是 UTF-16LE（工作目录、参数、图标、相对路径），
  `LinkInfo` 段是 **ANSI**（绝对目标路径）。
  目标与快捷方式**跨盘符**时写不出相对路径，`LinkFlags` 的
  `HasRelativePath`(0x08) 会关掉（实测 `0xff` → `0xf7`，文件少 56 字节），
  此时目标路径**只存在于 LinkInfo 里**
- **修法**：断言时两段都要翻（UTF-16LE + latin-1），见
  `tests/test_shortcut.py::lnk_strings`；并补了一条跨盘符的回归测试
- **教训**：二进制格式的字段可能有多份冗余副本，只查一处会得出错误结论

### P8 —— `ttk.Combobox` 忘了接 `textvariable`，`current()` 只改显示不改值

- **现象**：界面上把「匹配强度」从默认改成「宽松」，跑出来还是默认的 3
- **根因**：建 Combobox 时只把 `StringVar` 存进了自己的字典，**没传给控件**。
  `widget.current(index)` 改的是控件的显示文本，而我们读的是那个没人管的变量
- **修法**：`ttk.Combobox(..., textvariable=var, ...)`
- **教训**：**下拉框这种「显示文本 ≠ 取值」的控件，最容易出「选了没用」的 bug。**
  测试要断言**取值**（`--min-score 1`），不能只断言显示文本

### P9 —— 这个执行环境在独立的窗口站上，抓屏抓不到自己的窗口

- **现象**：`tkinter` 建窗口成功，`IsWindowVisible`/`winfo_ismapped` 全是 1，
  几何尺寸也对，但 `PIL.ImageGrab` 抓那块区域只有桌面壁纸
- **根因**：命令是在**另一个 window station / desktop** 上跑的，窗口确实存在于
  那个桌面上，只是不在被 GDI 抓屏的那个桌面
- **影响**：**AI 自己看不到界面**。界面的观感、弹窗手感，只能由人确认
- **替代做法**：把活着的控件树 dump 出来（`winfo_x/y/width/height` + 配色 + 字体），
  用 Pillow 按这些**真实坐标**渲染成预览图。坐标是 Tk 算的，版式可信；
  只有字形渲染会有 1px 级出入。别再浪费时间反复尝试抓屏

### P10 —— `git add -A` 把仓库里的临时文件一起提交了

- **现象**：提交信息文件 `_commitmsg.txt` 出现在那次提交里；`rm` 掉之后
  `git status` 一直显示一行 `D _commitmsg.txt`
- **根因**：为了避开 heredoc 里的中文被安全策略误判，把提交信息写成了文件
  `git commit -F _commitmsg.txt`，但**文件建在了仓库根目录**，
  而 `git add -A` 不看文件名，一律 stage
- **修法**：当时**没有远端、`main` 就是最新**，所以
  `git rm --cached _commitmsg.txt` + `git commit --amend --no-edit` 就地清掉。
  之后改成把提交信息写到 `%TEMP%`，用绝对路径 `git commit -F` 引用
- **教训**：`git add -A` 之前先想「仓库目录里有没有我的中间产物」。
  另外 —— **改历史（amend / reset）之前必须先确认没远端、且自己就是最新**，
  否则会毁掉别人的工作

### P11 —— 自己的文档里数字对不上

- **现象**：整理文档时发现两处对不上：
  README / TODO 里写的**用例总数**比实际少，
  AGENTS 的「新增规则怎么加」里写的**「当前最大编号」**落后了好几个编号
  （写着最大是 `R17`，实际已经加到 `R22`）
- **根因**：加测试、加规则时只改了「正文」，忘了改散布在别处的**汇总性数字**
  （用例总数、最大编号、§4/§5 的编号范围索引）
- **修法**：把汇总数字当成「需要同步更新的引用」；收尾时按 §7.4 的命令全仓搜一遍。
  更彻底的办法是**干脆不写死数字**（比如不再记录每一轮的用例条数）
- **教训**：**文档里凡是「总数、最大编号、第 N 条」这类汇总数字，都会腐烂。**
  能改成「见 §X」这种引用就别写死；非要写死，就写进 [§7.4](#74-最后跑一遍) 的收尾清单

### P12 —— 把工作簿里所有工作表的「名称」列合并成一个名单

- **现象**：用户报告 `gbcopy`「把不该拷的模型和图纸也拷过来了」。
  在现场 `D:\example\订单\0928` 里发现多拷了 **26** 个文件
- **根因**：`extract_names_from_sheets()` 遍历**所有**工作表，把每张表里
  「名称」列的内容**合并**成一个名单。那份工作簿有两张表：
  `采购清单`（6 个名称，真正要外发的）和 `备料参考`（41 个，只是参考）。
  合并成 47 个 → 参考页的 26 个零件也被当成待采购
- **修法**：只认一张表 —— `--sheet` 指定 > 名为「采购清单」的表 > 第一张候选；
  其余候选记进 `NameExtraction.skipped`，触发一条醒目提醒 + 给出 `--sheet` 出口
  （准则化为 [R24](#r24--从用户的文件里读一份数据时多份候选必须明确挑一份并说出来-2026-09-28)）
- **注意**：归档原版 `archive/manufacturing/采购文件自动匹配拷贝.py` 的
  `extract_names()` 是**同样的写法** —— 属原版遗留，不是重构引入。
  但这**不构成不修的理由**：用户在用这个工具，行为不符预期就是 bug
- **教训 1**：合并多份候选看着"更全"，实际是把用户**明确划出去**的数据又拉了回来。
  凡是"从用户的文件里读一份东西"，都得能说清「我读的是哪一份」
- **教训 2**：**测试也会把 bug 当成正确行为钉死。**
  当时有一条 `test_merges_multiple_sheets`，断言的正是"多表要合并"。
  修 bug 时得先把这条改掉 —— **看到老测试先问一句「它凭什么这么断言」**，
  别默认"测试通过 = 行为正确"

### P13 —— 改在临时副本上的东西，一同步就被本地覆盖回去  `2026-09-29`

- **现象**：给远端造好了 `speedup/` 子目录后，顺手在**外壳仓库的检出副本**里把
  `README` 的 `git clone <your-repo-url>` 占位改成了真实地址。提交推送一切正常，
  但回读远端发现**还是旧内容**
- **根因**：外壳仓库是 `sync-to-github.py` 在 `%TEMP%` 下临时建的，用完即删。
  更关键的是 —— 同步的语义是「**用本地仓库的内容覆盖远端 `speedup/`**」，
  所以外壳仓库里任何**本地不存在的**改动，下次同步必然被盖掉。
  我改的是副本，本地那份从来没动过
- **为什么容易中招**：外壳仓库长得就像个"正常的检出目录"，
  `cd` 进去改文件、`git commit` 全都能成功，**没有任何报错提示你改错了地方**
- **修法**：把改动落到**本地仓库**（改文件 → 本地 `git commit` → 跑同步脚本），
  让外壳仓库永远只是个搬运工，绝不手工编辑
  （准则化为 [R25](#r25--同步到远端必须从本地仓库发不许改临时副本-2026-09-29)）
- **另一个坑（同时踩到）**：`git read-tree --prefix=speedup/` 在
  **远端已有 `speedup/`** 时会报
  `Entry 'speedup/x' overlaps with 'speedup/x'. Cannot bind.`
  —— 首次添加能用，**后续更新就炸**。必须先
  `git rm -r --cached --ignore-unmatch speedup/` 清掉索引里那块（工作区残留也要删），
  再 `read-tree`。脚本里已处理，见 `sync-to-github.py` 第 4 步
- **验收方式的教训**：`git push` **返回 0 不代表推对了内容**。
  必须回读远端（`gh api repos/<owner>/<repo>/contents/<path>`）逐字比对

### 各条规则的具体理由

#### R1 全 Python，禁止 bat / psh

原工具靠 `.bat` 找 Python + PowerShell 弹窗，有三个问题：进程冷启动明显卡顿、
临时 `.ps1` 写盘被杀软误报、多行脚本引号易被剥导致语法错误。
详见 [P2](#p2--powershell-弹窗的三重代价)。

**验收**：`git ls-files | grep -E '\.(bat|cmd|ps1|vbs)$'` 无输出。

#### R2 不许把 stdout 强行改成 UTF-8

中文 Windows 控制台是 cp936，改 Python 侧编码会造成编码不匹配 → 全乱码。
详见 [P1](#p1--windows-中文控制台乱码)。

**验收**：`grep -rn 'reconfigure(.*encoding' src/` 无输出。

#### R3 面向 Windows 中文环境

路径用 `os.path` / `pathlib` 不手拼；文件名比较走
`os.path.normcase(os.path.abspath(...))`；要交给 VBE/VB6 等老式宿主的文本
（`.bas`、批处理、部分 ERP 接口文件）必须输出 GBK，不能 UTF-8 无 BOM。

#### R4 破坏性操作必须先说清楚

覆盖文件要在报告里明写「（覆盖旧文件）」；拷贝遇到同名文件一律跳过不覆盖
（目标里的同名文件可能是人工改过的，覆盖不可逆）；删除前先备份、先列路径、先确认。

#### R5 业务数据不进仓库

**仓库是公开的**，所以这条的范围比「别提交 xlsx」大得多：任何能反推出我们是谁、
给谁干活、在做什么产品的内容都不许进来。代码/注释/文档/测试数据一律用中性示例名，
路径走 `D:\example\...`。`archive/` 与 `docs/INVENTORY.md` 刻意不进 git。

2026-09-28 推公开仓库前做过一次脱敏，替换了 300 多处真实零件名、客户项目名和
绝对路径。**同一件事别再干第二次** —— 写的时候就用中性名。

#### R6 常量集中到 `config.py`

旧脚本把 `MODEL_EXTS` / `NAME_COL` 散在各文件头部，采购清单的列号在
生成侧和读取侧各写一份，改列就出事。

#### R7 纯函数优先，IO 与决策分离

拆开「匹配决策」与「拷贝执行」后，`--dry-run` 的实现变成
「只调 `plan_copies`，不调 `execute_copies`」，一行搞定，且完全可测。

#### R8 中文对齐用 `display_width`

`ord(ch) > 127` 会把 `…`、`—` 误判成 2 列，表格错位。
改用 `unicodedata.east_asian_width`。

#### R9 异常分层

用户能理解的失败抛 `SpeedupError` 子类，由 `cli.py` 统一打印 `[失败] xxx`；
未预期异常让它冒泡（便于开发期定位 bug），不要写 `except Exception: pass`。

#### R10 注释写「为什么」

关键决策要在 docstring 里留取舍理由，否则后人会「优化」掉它
（比如把 tkinter 换回 PowerShell）。

#### R11 类型注解 + 中文 docstring

公开函数必须带类型注解与 docstring，写清参数、返回、异常与非平凡的设计理由。

#### R12 先写测试再写实现

长期逻辑组件一律红→绿→重构。

#### R13 测试不许碰真实数据

用 `tmp_path` / `make_files` 夹具；`tests/conftest.py` 里有 autouse 夹具
打桩「打开资源管理器」这类副作用。

#### R14 测试里也别写业务魔数

需要常量就从 `speedup.config` 取，否则改常量时测试会「永远绿」，给出假安全感。

#### R15 已知边界要留回归测试并写明原因

`test_aluminium_grade_with_temper_is_strong` 钉死旧规则的漏判
（见 [P5](#p5--注释声称支持的格式实现其实不支持)）；
`test_does_not_switch_encoding_to_utf8` 钉死 R2；
`test_tools_are_wired_to_the_same_run_path` 钉死 [P3](#p3--parserset_defaults_runrun-把函数对象提前绑死)。

#### R16 GUI 测试要能跳过

真实点窗口的用例标 `@pytest.mark.gui`，默认跳过；其余逻辑必须能在
无图形界面环境跑通。

#### R17 测试失败先怀疑测试

首轮 8 个失败里 7 个是测试写得不严谨（样例数据选错场景），只有 1 个是真缺口。
看到红先复核断言与样例数据。

#### R18 换行符统一 LF，归档区不做转换

本机全局 `core.autocrlf=true`，首次 `git add` 每个文件都刷一条
「LF will be replaced by CRLF」警告。`.gitattributes` 里显式钉死 `eol=lf`，
并给 `archive/**` 加 `-text` —— 归档脚本若被转换换行，
`_PROVENANCE.md` 里记的 sha256 就对不上了。

#### R19 界面只拼 argv，走同一条 `run()`

图形界面不直接调业务函数，而是拼出 argv 交给 `cli.build_parser()` 解析，
再调 `module.run(args)`。菜单与命令行本来就这么做，界面接上同一条路，
三条入口共用一份逻辑。拼装步骤单独抽成 `ToolPage.build_argv()`，脱离窗口即可测。

#### R20 新增工具必须配界面表单

`gui.TOOL_FIELDS` 漏了某个工具，它就不出现在界面上 —— 用户会以为工具丢了。
`TestFieldContract` 会检查「表单覆盖所有工具」「每个 dest/flag 在 argparse 里真实存在」
「位置参数顺序与声明顺序一致」。

#### R21 日志区必须等宽、CJK 恰好 2 倍宽

`console.render_table` 按显示宽度对齐；日志框若用比例字体，`gbcopy` 那张
130 多列的匹配表会完全没法看。`TestFonts` 直接量字体宽度来锁死这个前提。

#### R22 `pythonw` 下必须 `ensure_streams()`

双击快捷方式走 `pythonw.exe`（为了无黑框），此时 `sys.stdout` 是 `None`，
第一句 `print()` 就会 `AttributeError`。`cli.main()` / `gui.launch()` 开头必须补流。
另外「有没有控制台」这个判断要在补流**之前**做，否则信息丢失。

**验收**：`tests/test_gui.py::TestPythonwMode`。

#### R23 临时文件不许写在仓库里

`git commit -F` 用的提交信息文件写在仓库根目录，`git add -A` 会顺手 stage 它，
于是临时文件进了历史（详见 [P10](#p10--git-add--a-把仓库里的临时文件一起提交了)）。
写到 `%TEMP%` 用绝对路径引用即可。

**为什么不加 `.gitignore` 挡**：根本问题是「仓库目录里不该出现中间产物」，
加规则只是把症状藏起来 —— 下次换个文件名照样中招。

**验收**：`git ls-files | grep -iE '_commitmsg|commitmsg'` 无输出。

#### R24 多份候选必须明确挑一份并说出来

`extract_names_from_sheets()` 把工作簿里所有带「名称」列的表**合并**成一个名单，
于是「备料参考」这张附页的 41 个零件也进了待采购清单，
白拷 26 个文件出去（详见 [P12](#p12--把工作簿里所有工作表的名称列合并成一个名单)）。

规则落地成四件事：**只挑一份 / 优先按名字挑 / 把选择讲出来 / 留手动入口**。
`NameExtraction` 这个返回值就是为了承载「用了哪张、忽略了哪张」而存在的 ——
用一句给人看的字符串塞这些信息，调用方就只能解析文本，那正是坑的藏身处。

**验收**：`tests/test_e2e.py::TestMultiSheetListing`。

#### R26 图纸提取按坐标切，不按文字流顺序

给采购清单补「表面处理」这一步时，先按最直觉的写法试了一版：
`extract_text()` 拿全文，再找「技术要求：」后面的行。结果捞出来的是

```
技术要求： 零 件 代 号 1、边角去毛刺，倒钝； 2、未注公差尺寸为±0.1mm
借(通)用件登记 3、未注倒角尺寸为C0.5； …
```

—— 技术要求条目和图框标题栏的文字**在纵向范围上重叠**，而 `extract_text()`
是「按 y 排序后逐行拼接」，两块内容于是交错着吐出来。按行取就是垃圾，
按「技术要求」往下数 N 行也永远数不对。

改用坐标后一次就干净了：条目和标题的 `x0` **完全相等**（实测 413.3），
而标题栏文字贴在页面左边缘（`x0` 6.8~63 那一带）。所以只要
`top > 标题 top` 且 `|x0 - 标题 x0| < 容差` 两个条件。

两个必须一起记的教训：

- **容差不能是唯一防线。** 容差取 6pt 时，仍有一份图纸的 `0.00` 混进来过
  （它的 `x0` 只差 7pt）。所以条目编号另收紧一道：只认顿号 ——
  尺寸标注用的是半角点，正好区分开。
- **「读不了」和「图纸没写」是两回事。** 混成一个「空」，汇总报告里就分不清
  是 pdfplumber 挂了还是图纸真没这句话；主人拿着清单去找加工厂时，
  会以为「这个零件不用表面处理」。所以前者给 `error`，后者给空结果（见 R9）。

**验收**：`tests/test_techreq.py`。

#### R27 报「没找到」必须说明「实际扫到了什么」

`gbbuild` 报出「2 个零件没有同名图纸」之后，用户的第一反应**不是**
「那两个零件确实没图纸」，而是「你肯定跑去别处找同名文件了」——
因为**用户看不见搜索过程**，只能从结果反推，而反推往往是错的。

当时还真的存在「同名不同内容」的图纸：同一个零件名在三个版本目录里都有，
两份写「参考CMF」、一份写具体的阳极氧化。用户手上拿的是哪一份，
直接决定「工具有没有读错」这个判断 —— 而这件事**工具必须自己说清楚**，
不能指望用户去猜。

修法：报「没有同名图纸」时，顺手把那个文件夹里**实际存在**的 PDF 列出来，
并附一句判断方法（「缺的零件若不在这批文件名里，就是名字对不上」）。
这样「东西真不在」和「在、只是名字对不上」一眼就能分开。

**验收**：`tests/test_e2e.py::TestGbbuildEndToEnd::test_missing_pdf_lists_the_folder_pdfs`
与 `::test_missing_pdf_when_folder_has_none`。

#### R28 读 PDF 只取页面范围内的内容

用户报「腕驱动连杆V2 的表面处理，你写成电镀，图纸上明明是本色硬质阳极氧化」。
把那个 PDF 的坐标挖出来，真相是这样的（页面 595 x 842）：

```
'技术要求'                x0=  79.4  top= 553.9   ← 页内，屏幕上看得见
'2、表面本色硬质阳极氧化；'    x0=  79.4  top= 588.7   ← 页内 ✓
'技术要求：'               x0= 627.9  top= 523.8   ← ⚠️ 超出页宽 595
'5、外观件，表面电镀处理。'    x0= 627.9  top= 641.0   ← ⚠️ 页外
```

**这个 PDF 里藏着两张图纸**，第二张排在 x=595 之后（被裁掉、屏幕上看不见），
而 `extract_words()` 照样把它读了出来。它的 `top` 更靠上，于是抢在了页内那份前面。

最要命的是**结果毫无破绽**：「电镀」是个合法的表面处理，程序不会报任何异常。
全盘 113 个「模型+图纸」配对里只有 5 个中招，而**哪几个中招取决于两套词在
`extract_words()` 里的先后顺序** —— 同一批 5 张图纸里 3 张碰巧读对、2 张读错。
用户不回去核对原图，这事儿就永远埋在表格里。

修法：新增 `pdfpage.words_in_page(page)`，只保留落在页面矩形内的词
（留 0.5pt 容差防浮点误差误杀贴边字）；`material.py` 的材料识别与
`techreq.py` 的技术要求提取统统改走它。

**验收**：`tests/test_pdfpage.py`。

#### R29 重依赖必须做成可选，且运行时优雅降级

给采购清单加轴测图，选了 cadquery。装完才发现它捎带了一串：OCP、vtk、numpy、
scipy、numba、trame ×5 —— `uv pip install` 跑了 **4 分 46 秒**，几百 MB。

问题不在「装得久」，而在**这份负担会被强加给所有人**：只想要「读 PDF 出清单」
的用户，凭什么为了一个锦上添花的图片列去装 OpenCASCADE？所以：

1. 进 `[project.optional-dependencies]`，`pip install speedup[images]` 才装
2. `thumb.py` 用 `_load_cadquery()` 延迟导入，缺依赖时 `is_available()` 返回
   False、渲染返回带 `error` 的结果 —— 调用方不用 try/except，也不该崩
3. 测试用 `pytest.importorskip()`，纯计算部分（相机位置、尺寸换算）不碰重库，
   所以**没装 cadquery 的机器上测试照样全绿**
4. 命令行明说「没装 cadquery，已跳过轴测图（装法是 …）」，别静默

**验收**：`tests/test_thumb.py::TestIsAvailable::test_false_when_cadquery_missing`
与 `::TestRenderWithoutCadquery::test_reports_error_instead_of_crashing`。
